# Premiere Gotchas

Real-world Premiere MCP behaviour — limitations, bugs, workarounds and lessons learned.
**Every entry here was observed by running the tool against a live Premiere session**, not
inferred from source.

**Source-of-truth: mixed.**

## The one rule

This rule overrides every individual tool-specific recommendation below.

**Never report an operation as successful on the strength of a tool response.**

The expanded tool dispatcher ends with a catch-all that returns success for any tool it
never implemented. A large share of the advertised tool surface therefore returns
`success: true` while doing absolutely nothing.

**Verified live:** deleting a project item returned `success: true, accepted: true` — and the
item was still in the project afterwards.

### How to tell at runtime

| Signal | Meaning |
|---|---|
| Response contains `"accepted": true` **and** the note *"Expanded tool dispatched through the native Premiere bridge"* | **Nothing happened.** |
| Response contains real data — IDs, names, counts, durations, before/after values | The tool did something. |

**Always confirm a write with a read.** `get_project_info`, `list_sequence_tracks`,
`list_project_items`, `get_clip_at_position`. If it cannot be confirmed, say it needs doing
by hand — do not report success.

*Counts and the full tool lists: `TOOL-RELIABILITY.md`.*

## The bridge

**The bridge follows whatever project is frontmost in Premiere.**

It silently switched from one project to another mid-session and very nearly caused work in
the wrong project. Nothing warns you.

- **Call `get_project_info` and confirm the project name before every build step** — not
  once at the start of a session.
- If tool calls hang or time out, the bridge is not running. That is the cause roughly nine
  times in ten. Check the panel before debugging anything else.
- After restarting Premiere, stopping and restarting the bridge is enough — the extension
  stays installed.
- A panel that looks stuck can be right-clicked → `Reload`.

*Startup procedure and the fastest liveness check: `CLAUDE.md`.*

## Sequences

### `create_sequence` ignores the format you ask for

It **always** produces a 1080×1920 / 30fps sequence regardless of the project item or
settings passed. Independently corroborated: a request for 3840×2160 / 23.976 also came back
as the default preset.

Worse, it cannot be corrected afterwards — `set_sequence_resolution` and
`set_sequence_frame_rate` are both no-ops. So are `create_sequence_from_clips` and
`create_sequence_from_preset`.

**The workaround, and the only reliable way to get a correctly-formatted sequence:**

```
1. duplicate_sequence  from one that already has the settings you want
2. empty the copy       (loop removal per clip — see below)
3. build into the copy
```

`delete_sequence` **does** work, so a bad sequence can be cleaned up.

## Timeline placement

- **`add_to_timeline` floors `sourceOutPoint`**, so a clip lands roughly one frame short. Add
  half a frame to the out point when exact length matters.
- **Prefer assembling with source in/out points** over razor-then-delete: one call per clip,
  deterministic, and it never disturbs clips already on the timeline.
- **Never hand-compute timeline offsets.** Premiere converts seconds to frames *two different
  ways* — source points are floored, timeline positions are rounded. Getting this wrong
  produces a one-frame black gap between every clip, invisible in the tool response and
  obvious on playback. The derivation and the script that handles it are in `CLAUDE.md`.

## Removal and cleanup

| Behaviour | Detail |
|---|---|
| **Bulk delete is unavailable** | `select_all_clips` / `remove_selected_clips` both fail in the CEP context. **Loop removal one clip at a time.** |
| **Video removal does not take its linked audio** | Remove the audio separately, targeting the audio track type. |
| **`remove_from_timeline` misreports its mode** | It reports `deleteMode: "ripple"` even when explicitly passed `ripple: false`. It did **not** actually ripple — all downstream start times were verified unchanged — but **re-verify with `list_sequence_tracks` after every removal.** |
| **`delete_project_item` is a no-op** | Confirmed live. Removing an imported clip from the project panel must be done by hand in Premiere. `delete_multiple_project_items` likewise. |
| **`move_item_to_bin` takes `targetBinId`** | Not `binId`, not `binName`. The wrong key fails schema validation, so **check `success` rather than assuming it filed.** |
| **Passing a bin name at import does not reliably file anything** | Import, then move the item explicitly. |

## Markers

| Behaviour | Detail |
|---|---|
| **`list_markers` works** | Returns real IDs, names, comments and durations. It is also **the only way to get the IDs needed to delete a marker.** |
| **The other marker readers do not** | `get_sequence_markers` returns 0; `get_sequence_markers_by_type` and `get_full_sequence_info` return stubs. |
| **`add_marker` supports colour and duration** | Colour as a name string; a duration makes it a span marker. |
| **`update_marker` cannot change duration** | It can change name, comment and colour only. **To change a span, delete the marker and re-add it.** |
| **Markers ripple with clips** | Verified: an edit shifted a run of clips left by 3.387s and the markers moved with them, staying aligned. This is usually what you want — but it means a marker is not an independent anchor. |

## Effects

- **`remove_effect` does not exist.** Premiere's API cannot remove an applied effect. If the
  wrong effect is applied, **call undo immediately** rather than trying to strip it
  afterwards. Plan effect application accordingly.
- 2D parameters need the local `set_param_value` addition — the stock position and scale
  tools are among the no-ops. See `design-system.md` for the logo case and `CLAUDE.md` for
  the tool itself.

## Verification

**`export_frame` is real, but conditionally trustworthy.**

| Use | Reliability |
|---|---|
| Confirming a static overlay actually landed | **Reliable.** Fastest available proof. |
| Grabbing an arbitrary time on a long sequence | **Unreliable.** Returned stale or incorrect frames for two of three probes, while structural reads confirmed the timeline was correct. |

So: **verify structure with `list_sequence_tracks` and `get_clip_at_position`; verify
appearance with `export_frame`** — and do not conclude the timeline is wrong because a still
looks wrong.

Two more notes:

- **`export_frame` appends its own extension.** Passing a filename that already ends in an
  image extension produces a doubled one.
- **`list_sequence_tracks` does not return source in/out points.** Use
  `get_clip_at_position` when you need them.

## Media and rendering

- **Alpha WebM does not import into Premiere.** Always transcode to ProRes 4444. The ffmpeg
  input needs the VP9 decoder specified explicitly, or **the alpha channel is silently
  dropped and you get a black box** that imports without error.
- **A composition must set a transparent background** or the alpha render is an opaque
  rectangle covering the footage beneath it.
- **Premiere links media by file path.** Re-rendering over a path Premiere already has linked
  makes it serve cached media or lose the frame reference. **Always render a revision to a
  new unique filename.** See `production-workflow.md`.
- **Rational frame rates must survive as strings.** A numeric coercion in the render script's
  argument parser once turned `60000/1001` into `NaN`; fixed, but worth knowing the failure
  mode if a render silently comes out at the wrong rate.

## Audio

**Premiere's scripting API cannot read audio levels at all.** There is no way to measure
loudness from inside the MCP.

- To target a loudness figure, **measure with ffmpeg first**, then set gain from the measured
  value. See `presets/README.md`.
- **`detect_silence` needs ffmpeg on PATH** and reads the media file directly rather than
  going through Premiere. It only **reports** intervals — it never cuts anything.
- Apply a limiter **last** in an effect chain, so it catches whatever earlier stages let
  through.

## Export

| Constraint | Detail |
|---|---|
| **Preset must be an absolute `.epr` path** | Format names like "mp4" or "h264" are rejected outright. |
| **Adobe Media Encoder must be running** | Export queues to AME. |
| **Rendering is asynchronous** | The call returns before the file exists. |
| **Export strictly sequentially** | Wait for each file to stop growing. Queuing several at once risks every job picking up the last in/out points set. |
| **`get_render_queue_status` requires AME** | Returns an honest error without it — one of the tools that fails truthfully. |

*Full export procedure and post-export verification: `production-workflow.md`.*

## No scripting escape hatch

Worth stating explicitly, because it is the natural next idea when a tool turns out to be a
no-op:

- **`execute_extendscript` is one of the no-op tools.**
- **`evaluate_expression` resolves property paths only** and cannot mutate anything.

So arbitrary ExtendScript cannot be used to work around a broken tool. If no working tool
does the job, it is a manual step in Premiere. Say so rather than reaching for a hatch that
does not open.

## Environment

- **`timeout` does not exist on macOS.** Do not use it in scripts — background the process and
  kill it instead.
- Transcription writes an intermediate file into whatever directory it is pointed at; the
  project's transcription script uses a scratch directory so it never litters the source

## AME renders stall partway (observed 2026-08-11)

`export_sequence` queues successfully and returns a real `jobID`, but the render **stops
partway and never resumes** — verified by watching file size for 90s with zero growth.
Truncation points are inconsistent and not clip-aligned (2.6s on one sequence, 6.43s
mid-clip on another), so it is not a work-area or in/out problem: both read back correct.

**Diagnosis is blind from the bridge.** `get_render_queue_status` returns
`available: false` — there is no queue telemetry, and AME's error state is only visible in
its own window.

**What to check first:** open Adobe Media Encoder and look at the queue for failed items.
A queue with accumulated failed jobs from earlier in a session appears to be the trigger;
clearing it (or restarting AME) is the first thing to try before re-queuing.

**Contributing factor to avoid:** re-rendering a graphic **over a path Premiere already has
open** and relying on `refresh_media`. `design-system.md` already says to render to a new
unique filename every time; overwriting in place and refreshing is not a reliable
substitute, and this session hit it repeatedly.


## Transitions (observed 2026-08-12)

### `add_transition` applies to the START of `clipId1`, not its end

To place a transition on the cut between clips N and N+1, pass clip **N+1** as `clipId1`.

Verified: passing the clip that starts at 5.2386s produced a transition spanning
5.1218–5.3720s — centred on that clip's **start**. Getting this wrong puts every transition
one cut early.

- **`clipId2` is ignored entirely.** The implementation signature names it `_clipId2`.
- **`duration` is honoured exactly.** 0.25s → 15 frames at 59.94fps.
- Alignment is centred on the cut, so **handles are required on both sides**.

### `add_transition` always returns `success: false` — it is a false negative

The error reads *"Transition call completed but Premiere Pro did not expose a verified
transition change"*, with `before` and `after` both `available: false`.

**Cause:** `transitionVerificationScript()` in `src/tools/index.ts` probes `numTransitions`
on the QE **clip** object, but Premiere 2026 stores transitions on the **track**. The probe
finds nothing to read either way, so verification can never pass.

**All 10 transitions applied in this session returned `success: false`, and all 10 landed.**

This is the inverse of the usual failure mode in this file — normally a tool lies about
succeeding. Here it lies about failing. Do not retry on `success: false`; you will double up.

### How to actually verify a transition

`evaluate_expression` resolves these property paths:

```
app.project.activeSequence.videoTracks[0].transitions.numItems
app.project.activeSequence.videoTracks[0].transitions[i].name
app.project.activeSequence.videoTracks[0].transitions[i].start.seconds
app.project.activeSequence.videoTracks[0].transitions[i].end.seconds
```

**Capture the baseline count before the first call.** Skipping that made it ambiguous
whether an existing transition was pre-existing or newly created, and cost a round of
investigation to resolve.

Note these times are **absolute sequence time**, matching `list_sequence_tracks`.
`get_clip_at_position` returned times 0.5005s *lower* on the same sequence — a zero-point
offset. Do not compare the two directly.

### There is no `remove_transition` tool

`undo` works and is the only programmatic removal — verified, count went 3 → 2 and removed
only the most recent transition. Otherwise it is a manual delete in Premiere (select the
transition, press Delete), which is cheap, so a wrong transition is low-stakes.

### Motion Bro cannot be driven from the bridge

It is a CEP panel with its own UI and no scripting hook, and `execute_extendscript` is a
no-op. Native transitions only. `list_available_transitions` returned **110** on Premiere
2026, including the modern set — Zoom Blur, Whip, Flash, Earthquake, Glitch, VHS Damage,
Light Leak, Spin Motion, Pop Motion — which covers the high-energy vocabulary without it.
